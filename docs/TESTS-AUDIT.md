# Аудит браузерных проверок: что перенести в юниты и как дойти до минуты

Разбор всех 148 e2e-проверок: кому из них правда нужен браузер, что переносится
в юниты, что мешает коду быть тестируемым и из чего складывается прогон за минуту.
По состоянию мерджа `bf3235b` (ускоренное время уже вехало: `TIME_SCALE=10`,
`sceneReady` по признаку). Все числа ниже — замеренные, не прикидочные.

## Замеры (4-ядерная машина, этот контейнер)

| Что                                       | Результат            |
| ----------------------------------------- | -------------------- |
| Юниты: 132 теста                          | **2,3 с**            |
| Сборка (vite build)                       | 1,1 с                |
| e2e, 2 воркера (умолчание: половина ядер) | 3м26с, 1 флак        |
| e2e, 8 воркеров                           | **1м43с**, 2 флака   |
| e2e, 14 воркеров                          | 2м52с, 4 флака       |
| Процессорное время полного прогона        | ~78 с на 206 с стены |

Три вывода из этой таблицы:

1. **Прогон на ~60–90% состоит из ожидания.** 78 секунд CPU на 3,5 минуты стены —
   тесты в основном спят или ждут переходов, и параллелить их можно смелее числа ядер.
2. **Но потолок есть, и он процессорный**: каждая открытая страница непрерывно
   рисует анимированную сцену (качка, рябь), и на 14 воркерах кадры проседают —
   жестовые проверки с фиксированными паузами перестают успевать и флакают,
   а весь прогон замедляется. На 4 ядрах оптимум ≈ 8.
3. **Все флаки при разгоне — жестовые тесты с фиксированными паузами**
   (`dragAt` 200 мс, `waitForTimeout(600)` после свайпа): пауза рассчитана на
   ненагруженный браузер, под нагрузкой переход не успевает. То есть замена пауз
   на событийные ожидания — не только скорость, но и пропуск к параллельности.

## Правило: когда браузер обязателен

По инвентаризации всех 148 тестов браузер честно нужен там, где проверяется:

- **каскад и раскладка**: flex-wrap, sticky, `@container`, специфичность
  селекторов, `::-webkit-scrollbar`, вычисленные значения переменных;
- **покадровое движение**: монотонность переходов, синхронность двух анимаций,
  Web Animations API, скриншот стыка цикла воды;
- **жесты и их арбитраж**: drag/fling, конкуренция с выделением и прокруткой,
  hit-test по слоям, потерянный указатель;
- **браузерные API**: clipboard, sessionStorage через reload, inert, getSelection.

Браузер НЕ нужен там, где тест по сути читает из DOM результат чистой функции
или бэкенд-операции и сравнивает с эталоном. Хорошая новость: исчезнувшей механики
в наборе нет, откровенных дублей мало — набор здоровый, он просто делает часть
юнитовой работы дорогим способом.

## Что переносится в юниты целиком

Самая жирная брешь — **`localBackend` не покрыт юнитами вовсе** (это уже отмечено
в REVIEW §Контракты). Семь проверок из `channel.spec.ts` гоняют браузер ради
логики, которая живёт в бэкенде и рендера не касается:

| Тест                                                  | Что на самом деле проверяется   |
| ----------------------------------------------------- | ------------------------------- |
| «сообщение из соседней вкладки доезжает»              | доставка через BroadcastChannel |
| «уход отмечается в ленте…» (notice-объект)            | запись `leave` + notice         |
| «каждая перемена при переоснащении — своё сообщение»  | `refitNotices` → 3 записи       |
| «старший отмечен и высаживает…»                       | правило `kick`                  |
| «не старшему высаживать нечем, старшинство переходит» | пересчёт `channel.owner`        |
| «перестановка из соседней вкладки не затирает свою»   | очередь `exclusive`             |
| «два корабля не встают на одно место»                 | та же очередь, гонка на место   |

Всё это — один новый файл `src/backend/localBackend.test.ts`: два инстанса бэкенда
на общем моке localStorage, `BroadcastChannel` в Node 22 есть нативно,
`navigator.locks` в jsdom нет — нужен маленький in-memory замок в тесте (десяток
строк), и это плюс: очередь тестируется управляемо, гонку можно сделать
детерминированной. Показательно, что «два корабля не встают на одно место» —
**единственный тест, падавший даже на 2 воркерах**: гонка, проверяемая через два
реальных браузера, воспроизводится по погоде; юнитом она проверяется точно.
Браузеру из этих семи оставить один сквозной smoke: «сообщение из вкладки A видно
во вкладке B» — что провода подключены, а не как работает коммутатор.

Ещё кандидаты на полный перенос (рендер без браузерной специфики — vitest + jsdom
или готовые чистые функции):

- «свой новый канал открывается сразу формой» — рендер по признаку владения;
- «ушедший остаётся в ленте с аватаркой» — `authorLook`/`MemberRef` (чистые);
- из errors.spec: правила «занятый позывной/номер», «слишком длинное не уходит» —
  проверки `join`/`limit` (лимиты уже покрыты `limit.test.ts`; браузеру остаётся
  по одному smoke на «отказ показан и выход есть»).

## Что «наполовину»: логика уже (или легко) юнитится, браузеру — доставка

Большой класс (~30 тестов): браузерный тест пересчитывает то, что уже проверено
юнитами (`allowedLayout`, `chatMagnets`, `settleMagnet`, `sailSeconds`,
`placement.ts`), и его настоящая ценность — «React и правда применил эти числа
к разметке». Их не надо переносить — их надо **сузить**: ассертить применение,
а не перевычислять правило. Примеры: «в тесном лежачем окне разговор не бывает
уже минимума» (это `chatLimits`), «пустая вкладка открывает треть» (это
`defaultWish`), «ход корабля с правдоподобной скоростью» (это `sailSeconds`,
покрыт юнитом; тест даже не дожидается хода — только читает CSS-переменную).

Две дыры, где юнита пока нет и потому браузерный тест несёт правило на себе:

- **`wavePhase`** (фаза качки) — локальная функция SeaScene, не экспортирована;
  тест «качка идёт волной» проверяет её через `animation-delay`. Экспортировать,
  покрыть юнитом — браузерный тест сожмётся до «фаза доехала до стиля».
- **`slotDepth`/`slotShare`/перспектива рейда** — юнитов нет, и все геометрические
  тесты сцены несут правило на пикселях. После выноса `laneStyle` в чистую функцию
  (она уже почти чистая, SeaScene.tsx:695–724) юнит проверяет числа перспективы,
  браузер — один тест «стили доехали».
- **Жизненный цикл манёвров** — после `fleetMotion` (SIMPLIFY этап 4) правила
  «перезаход = уход + пауза + заход», «вернулся — передумал уходить» уходят
  в юниты; самый долгий тест набора («на тесной линии уступает мельче»,
  `test.setTimeout(240000)`, 4–5 полных ходов подряд) сожмётся до одного хода:
  правило уступания — юнит `fleetLefts`, браузеру — что резинка доехала до CSS.

## Фантазии из вопроса — что из них окупается

- **«Полная модель UI в одном месте»** — да, и это то же самое, что уже предложено
  в SIMPLIFY/SHEETS по другим причинам: состояние раскладки уже модель
  (`useLayout`), состояние манёвров станет моделью (`fleetMotion`), состояние
  шторок — пять осей (SHEETS.md). Дешёвое тестовое следствие: в сборке для
  проверок публиковать снимок этих моделей в `window.__navy` (флагом, как
  `timeScale`) — и половина «где что стоит» ассертится мгновенным `evaluate`
  вместо чтения пикселей. Правило гигиены: модель — источник, из которого рисует
  сам UI, а не параллельная сводка для тестов (иначе она врёт ровно тогда, когда
  нужна).
- **«Лог действий/перемещений»** — в виде отдельной подсистемы не окупается,
  но журнал переходов `fleetMotion`-редьюсера (список `{id, phase, at}`) — это
  три строки в редьюсере, юниты по нему читаются как сценарии, а e2e может
  спросить «манёвр кончился?» вместо опроса DOM с таймером.
- **«Полная модель сцены»** — уже есть по частям: `placement` (кто где) +
  `shipMotion` (как идёт) + будущий `fleetMotion` (что происходит). Собирать их
  в отдельную над-модель не нужно — нужно доэкспортировать дыры (wavePhase,
  laneStyle) и перестать пересчитывать их в тестах.
- **«Тупо распараллелить»** — да, но с двумя оговорками из замеров: воркеров
  ставить ~200% ядер (на этой машине 8: минус половина времени одним изменением
  конфига), а пропуском к этому служит замена фиксированных пауз на события —
  иначе параллельность конвертируется во флаки. В `playwright.config.ts`:
  `workers: process.env.CI ? '100%' : '200%'`.

## Куда уходит время и как дойти до минуты

Раскладка расходов (по инвентаризации):

- `layout.spec.ts`: **~79 с чистого сна** в фиксированных `waitForTimeout`
  (72 вызова + кратность в хелперах: `skyFrames` 4×700 мс — трижды на соседних
  тестах, `leadChat`/`leadSide` по 840 мс — десятками);
- `scene+channel+errors`: ~25 с сна + ожидания реальных ходов (`SAIL`, до 5 подряд
  в одном тесте) + **два теста, живущих в реальном времени** (сбор кадров 7,2 с
  и 5 с интервалами вкладки, которые `timeScale` не ускоряет) + два `unhasten`;
- всё остальное — навигации (148 × goto+sceneReady) и сами переходы.

План, каждый шаг самостоятелен, с ожидаемым эффектом на этой машине:

1. **`workers: '200%'`** — 3м26с → 1м43с. Один диф в конфиге.
2. **События вместо пауз** — убирает и ~100 с суммарного сна, и флаки под
   нагрузкой. Конкретно: `dragAt`/`leadChat`/`lowerForm` ждут `expect.poll` по
   положению коробки, а не 600–840 мс; после свайпов — poll по `transform`;
   `WRITE_MS` → `expect.poll(readState)`. Хелперов немного, тестов они покрывают
   десятки. Ожидание: полный прогон на 8 воркерах ≈ 60–75 с.
3. **Долгие — первыми.** Критический путь параллельного прогона — самый долгий
   тест: «на тесной линии уступает мельче» (~30–40 с реального времени) плюс два
   реально-временных теста кадров. Вынести их в отдельный файл, который сортировкой
   имён встаёт в начало очереди (`tests/0-long.spec.ts`) — хвост прогона перестаёт
   ждать их в одиночестве. (А после `fleetMotion` «тесная линия» сожмётся до
   одного хода — см. выше.)
4. **Слить утроенную подготовку неба** («небо опущено», «уход не двигает небо»,
   «облака держатся горизонта» — трижды один `skyFrames` по 2,8 с) в один тест
   с тремя блоками ассертов: −5,6 с. Параметризовать пары «телефон/десктоп»
   («места на рейде», байт-в-байт) и «под кадром/сбоку» (точки магнита) — минус
   дублирующиеся навигации.
5. **Юниты по списку выше** — минус ~10 браузерных тестов и их навигации,
   плюс закрытие реального флака гонки. Юнит-набор вырастет со 132 до ~170,
   останется в пределах 3–4 с.

Итог по шагам 1–4: **~60 секунд полного прогона на 4 ядрах** (на 8-ядерной
машине разработчика — быстрее), без потери ни одной проверки. Шаг 5 добавляет
запас и точность. Минута — не предел: следующий уровень — `window.__navy`-модель
вместо чтения пикселей в «наполовину»-тестах, но это уже стоит делать вместе
с рефакторингами SIMPLIFY, а не отдельной кампанией.

## Пофайловые вердикты (сводно)

Полные таблицы по каждому тесту собраны при аудите; здесь — итог по категориям.

**layout.spec.ts (85):** браузер обязателен ~55 (каскад, жесты, покадровость,
z-index, скроллбары, sticky, container queries); «наполовину» ~25 (числа из
`allowedLayout`/`chatMagnets`/`chatLimits`/`defaultWish` — сузить до «применилось»);
явный дубль 1 («места на рейде» телефон/десктоп — параметризовать); слить 3
(тройка `skyFrames`); самый тяжёлый — «лента мотается после того, как разговор
погоняли по точкам», ~10 с сна (стресс-тест, оставить, но перевести на poll).

**scene.spec.ts (34):** браузер обязателен ~20 (анимации, скриншот воды, hit-test
по слоям, морзянка во времени, типографика карточки); «наполовину» ~13 (правила
из `placement`/`shipMotion` — сузить; wavePhase и перспектива — сначала
доэкспортировать юниты); реального времени два теста (7,2 с и 5 с) + два
`unhasten` — кандидаты в `0-long.spec.ts`.

**channel.spec.ts (24):** перенести в юниты 7 (таблица выше) + 2 рендерных;
браузер обязателен ~13 (выделение текста, clipboard, прицеп ленты, тактильные
состояния плашки, container query бэджа); частичный дубль 1 (вымпел старшего
в списке и в карточке — второй сжать до одной проверки текста).

**errors.spec.ts (5):** «наполовину» все — правила уже в юнитах (`limit`, `slug`)
или переносятся (`join`-конфликты); браузеру оставить по smoke на «отказ показан,
выход есть» — это их настоящий предмет (см. `expectWayOut`).

## Санитарная заметка

Один тест флакает уже на 2 воркерах: «два корабля не встают на одно место, даже
если выбрали его разом». Это не поломка набора — это гонка, которую браузерный
тест по своей природе воспроизводит недетерминированно. Правильное лечение —
перенос в юнит очереди (см. выше), а не ретраи.
