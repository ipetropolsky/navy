# API бэкенда

Фронтенд не знает, где лежат данные. Он знает только интерфейс `ChannelBackend`
(`src/backend/types.ts`) и берёт готовый экземпляр из `src/backend/index.ts`:

```ts
import { backend } from '@/backend';
```

Сегодня за этим интерфейсом стоит `LocalBackend` — эмулятор на `localStorage` и
`BroadcastChannel`. Завтра там окажется Firebase, и поменяется одна строка в
`src/backend/index.ts`. Всё остальное приложение останется как есть.

Как именно устроен этот переезд — какие заводятся коллекции, что добавляется в контракт
(статус отправки у сообщения, состояние связи, коды сетевых ошибок) и как себя ведёт
приложение без сети — в [FIREBASE.md](./FIREBASE.md).

## Правила, которые задают форму API

Общие правила проектирования контрактов — в [API-PRINCIPLES.md](./API-PRINCIPLES.md).
Ниже — то, что задаёт форму именно этого API.

- **Всё асинхронно.** Даже там, где реализация может ответить мгновенно. Синхронный ответ
  приучил бы интерфейс к порядку, которого у настоящего сервера не будет.
- **Всё адресно и одним именем.** У сущности ровно один идентификатор — `channelId`,
  `memberId`, `messageId`, `eventId`, — и называется он так же и в самой сущности,
  и в ссылке на неё: `message.author.memberId` и `member.memberId` — одно и то же поле.
- **Ссылка — объект, а не строка.** `author: { memberId }`, `thread: { messageId }`.
  Это уже пригодилось: рядом с id автора дописался снимок его вида (`look`), и читатели
  ссылки от этого не сломались.
- **Метод принимает один именованный объект, а возвращает тоже объект.** Адресные поля
  (`channelId`, `memberId`) лежат в нём скалярами — это адрес запроса, — а содержимое рядом,
  своим ключом: `sendMessage({ channelId, memberId, message })`.
- **Изменения возвращаются событиями, а не ответами.** Метод сообщает, что действие принято;
  состояние приложение обновляет по подписке. Событие приходит одинаково и на своё действие,
  и на чужое, поэтому в UI нет ветки «это сделал я».
- **По проводу идёт только то, что канал у себя оставляет.** Всё, что живёт ровно столько,
  сколько длится, — печать, оклик, — до бэкенда не доходит: см. [ниже](#печать-по-проводу-не-идёт).

## `channelId` и `slug` — это разные вещи

У канала два имени, и путать их не нужно.

|                 | `channelId`            | `slug`                              |
| --------------- | ---------------------- | ----------------------------------- |
| Зачем           | основной идентификатор | адрес в ссылке                      |
| Кто видит       | код                    | люди                                |
| Пример          | `ch-msm932km-f22usl`   | `nord-ost`                          |
| Меняется        | никогда                | да, `updateChannel`                 |
| Где встречается | все методы и события   | только в ссылке `?channel=nord-ost` |

Ссылка на канал выглядит как `?channel=nord-ost`. Приложение разбирает адрес один раз —
`getChannelBySlug({ slug })` — и дальше работает с `channel.channelId`. Всё остальное — подписка,
отправка, вход, выход — адресуется только идентификатором, поэтому смена адреса ничего
не ломает: ни привязка участника к каналу, ни доставка событий на неё не завязаны.

```ts
// Ссылка → канал: один раз, при открытии.
const snapshot = await backend.getChannelBySlug({ slug: 'nord-ost' });
const { channelId, title } = snapshot.channel;

// Дальше только channelId.
backend.subscribe({ channelId, onEvent: handle });
await backend.sendMessage({ channelId, memberId, message: { text: 'Курс норд' } });

// Адрес можно переназначить — channelId останется прежним, разговор не прервётся.
await backend.updateChannel({ channelId, channel: { slug: 'nord-ost-2', title } });
```

Требования к `slug`: только строчные латинские буквы, цифры и дефис между словами
(`/^[a-z0-9]+(-[a-z0-9]+)*$/`), не длиннее 40 символов, уникален среди каналов. Проверяет бэкенд:
`slug-invalid` — не та форма, `slug-taken` — занят. Для подсказки в интерфейсе есть
`slugify()` из `@/utils/slug`: он транслитерирует русское название, «Эскадра «Полночь»»
превращается в `eskadra-polnoch`.

## Сущности

```ts
// Канал целиком: сам канал и его коллекции, каждая своим ключом.
interface ChannelSnapshot {
    channel: Channel;
    members: Member[];
    messages: Message[];
}

interface Channel {
    channelId: string; // основной идентификатор, неизменный
    slug: string; // адрес в ссылке, меняется через updateChannel
    title: string;
    createdAt: number; // мс эпохи
    owner?: MemberRef; // старший на рейде; у пустого канала его нет
}

interface Member {
    memberId: string;
    name: string; // позывной, он же название корабля
    hullNumber: string; // ровно три цифры
    shipKind: ShipKind; // 'pr1234' | 'pr12412' | 'pr1141' | 'pr201' | 'pr205' | 'pr1258' | 'pr1400'
    color: string; // цвет позывного в ленте
    place: ShipPlacement; // место на рейде, назначает бэкенд
    joinedAt: number;
}

// Сообщение — это либо реплика участника, либо запись самого канала. Разбираются по `kind`.
type Message = ChatMessage | ShipNoticeMessage;

interface MessageBase {
    messageId: string;
    author: MemberRef; // кто отправил; у системной записи — тот, о ком она
    sentAt: number; // мс эпохи; как показать — дело интерфейса
}

interface ChatMessage extends MessageBase {
    kind?: undefined;
    text: string; // не длиннее MAX_MESSAGE_LENGTH = 500
    thread?: MessageRef; // ответ: сообщение, к которому он привязан
}

interface ShipNoticeMessage extends MessageBase {
    kind: 'system'; // пишет сам канал, а не участник
    notice: ShipNotice; // текста нет вовсе: только то, что случилось
}

interface ShipNotice {
    event: 'joined' | 'refit' | 'left' | 'kicked';
    before: ShipTitle; // каким корабль был; у входа и ухода — каким он был тогда
    after?: ShipTitle; // каким стал; только у переоснащения
    changed?: ShipField[]; // что именно поменялось: 'shipKind' | 'name' | 'hullNumber'
    course?: string; // куда пошёл; только у ухода, и только если корабль его назвал
}

// Как корабль звали в тот момент, о котором речь. Снимок, а не ссылка на участника.
interface ShipTitle {
    shipKind: ShipKind;
    name: string;
    hullNumber: string;
}

// Ссылки — объекты, а не голые строки. Рядом с id участника лежит снимок того, как корабль
// выглядел в тот момент: ссылка переживает самого участника — сообщение остаётся в ленте
// и после того, как корабль снялся с рейда, а искать автора среди нынешних участников
// тогда уже негде. Снимок кладёт тот, кто пишет сообщение; у ссылки на старшего его нет —
// она говорит о том, кто на рейде сейчас.
interface MemberRef {
    memberId: string;
    look?: AuthorLook;
}

// Каким корабль был виден в ленте: позывной, номер на аватарке, цвет подписи.
interface AuthorLook {
    name: string;
    hullNumber: string;
    color: string;
}
interface MessageRef {
    messageId: string;
}

type Side = 'left' | 'right';
type Corridor = 'left' | 'center' | 'right';

interface ShipPlacement {
    slot: number; // 0 — у горизонта, 9 — первая линия
    corridor: Corridor;
    left: number; // центр корабля, % ширины сцены
    facing: Side; // куда смотрит нос
    enterFrom: Side; // с какой стороны заплыл
    tried: Corridor[]; // коридоры, где корабль уже стоял на этом слоте
}

// Что за корабль на самом деле: по этим числам считается его ход в сцене.
interface ShipSpec {
    length: number; // длина наибольшая, м
    displacement: number; // полное водоизмещение, т
    knots: number; // полный ход, узлов
}
```

## Методы

| Метод                                           | Что делает                           | Возвращает                |
| ----------------------------------------------- | ------------------------------------ | ------------------------- |
| `getChannel({ channelId })`                     | Состояние канала целиком             | `ChannelSnapshot \| null` |
| `getChannelBySlug({ slug })`                    | Разбор адреса из ссылки              | `ChannelSnapshot \| null` |
| `createChannel({ channel })`                    | Заводит канал без участников         | `{ channel }`             |
| `updateChannel({ channelId, channel })`         | Меняет адрес и название канала       | `{ channel }`             |
| `join({ channelId, member })`                   | Ставит корабль в строй               | `{ member }`              |
| `updateMember({ channelId, memberId, member })` | Меняет позывной, номер, силуэт, цвет | `{ member }`              |
| `leave({ channelId, memberId, course? })`       | Выводит корабль из канала            | —                         |
| `kick({ channelId, memberId, member })`         | Высаживает чужой корабль             | —                         |
| `sendMessage({ channelId, memberId, message })` | Отправляет сообщение                 | `{ message }`             |
| `subscribe({ channelId, onEvent })`             | Подписка на события канала           | функция отписки           |

### Открыть канал и подписаться

```ts
const snapshot = await backend.getChannel({ channelId });
if (!snapshot) {
    // Канала нет: адрес устарел или канал не создавали.
}

const unsubscribe = backend.subscribe({
    channelId,
    onEvent: (event) => console.log(event.type, event),
});
// когда экран закрывается
unsubscribe();
```

### Создать канал

```ts
import { slugify } from '@/utils/slug';

const title = 'Эскадра «Полночь»';
const { channel } = await backend.createChannel({ channel: { slug: slugify(title), title } });
// channel.channelId — 'ch-…', channel.slug — 'eskadra-polnoch'
// дальше открываем ?channel=<channel.slug> и встаём в строй
```

### Место на рейде назначает бэкенд

Участник выбирает позывной, номер, силуэт и цвет — но не место в сцене. Слот, коридор,
точку внутри коридора и сторону входа выбирает бэкенд при `join` и кладёт в `member.place`.
Поэтому сцена у всех одинаковая: чей-то корабль стоит там же и смотрит туда же во всех
вкладках. Клиент только рисует то, что пришло, и ничего не досочиняет.

Правило простое: десять слотов по дальности, слот занимает один корабль, кадр поделён
на три вертикальных коридора, и два корабля в одном коридоре не встают ближе чем через
два слота друг от друга. Левый коридор вдобавок закрыт для трёх дальних слотов —
там остров, и корабль на нём выглядел бы выброшенным на берег. По той же причине на эти
слоты корабль заходит только справа: слева он прошёл бы прямо по острову.
Алгоритм — `src/backend/placement.ts`, а сколько и с какой скоростью кораблю идти,
считает `src/components/SeaScene/shipMotion.ts`.

### Место на рейде

Место выбирает человек — в форме корабля, огоньками на воде, — но приходит оно тем же путём,
что и всё остальное: полем `berth` в черновике участника.

```ts
await backend.join({ channelId, member: { ...draft, berth: { slot: 7, corridor: 'right', left: 80 } } });
// Место приедет обратно событием member-joined или member-updated — своё оно или чужое, не важно.
```

Выбор — пожелание, а не приказ. Пока человек заполнял форму, на выбранное место мог встать
кто-то другой; тогда бэкенд молча ставит корабль на случайное свободное — отказывать здесь
не за что, человек ничего не нарушил. Поля `berth` нет вовсе — место выбирает бэкенд
(при входе) или оно остаётся прежним (при переоснащении).

Свободные места считает чистая функция `freeBerths(taken)`, и она же экспортируется наружу:
форме нужно разметить рейд до того, как что-то отправлено, а считаются места из того же
списка кораблей, который у вкладки и так есть. `left` у места — ось коридора (20, 50 или 80%),
одна и та же на всех вкладках: место — это точка, и показать её человеку можно только такой.

Сцена сравнивает новое место с нарисованным: сменилось — корабль уходит за кромку, ждёт
три секунды и заходит на новое заново. Переползать по рейду он не умеет и не должен:
корабль снимается с якоря и приходит на новое место, а не сдвигается вбок.

### Встать на рейд

```ts
import { ChannelError } from '@/backend';

try {
    const { member } = await backend.join({
        channelId,
        member: { name: 'Гроза', hullNumber: '042', shipKind: 'pr12412', color: '#8ecae6' },
    });
    rememberMemberId(channelId, member.memberId);
} catch (error) {
    if (error instanceof ChannelError) {
        // error.code: 'channel-full' | 'name-taken' | 'hull-taken' | ...
        // error.message уже написан по-человечески, его можно показать в форме
    }
}
```

Вслед за `member-joined`, `member-updated` и `member-left` бэкенд сам пишет в ленту системную
запись и рассылает её обычным `message-added`. У таких записей стоит `kind: 'system'`, и текста
в них нет: приходят данные — что случилось, каким корабль был, каким стал и что в нём поменялось.

Одна запись — одна перемена. Сменивший разом тип, позывной и бортовой номер корабль даёт три
записи, а не одну с перечислением, и в ленте они встают тремя сообщениями: у каждого свой
`messageId`, своё `sentAt` и свой ответ. Порядок — от крупного к мелкому: сперва силуэт,
потом позывной, потом номер.

```jsonc
// встал на рейд
{ "event": "joined", "before": { "shipKind": "pr12412", "name": "Гроза", "hullNumber": "042" } }

// переоснастился: сменил тип, позывной и бортовой номер — три отдельных сообщения
{
    "event": "refit",
    "before": { "shipKind": "pr205", "name": "Буран", "hullNumber": "517" },
    "after": { "shipKind": "pr1258", "name": "Сирена", "hullNumber": "900" },
    "changed": "shipKind",
}
// ...и такие же записи с "changed": "name" и "changed": "hullNumber"
```

Фразу складывает интерфейс (`src/components/chat/ShipNoticeLine.tsx`), и получается из этого:

```
Малый противолодочный корабль встал на рейд
Теперь рейдовый тральщик
Теперь «Сирена»
517 теперь 900
Уходит с рейда. Новый курс: В Кронштадт, на зимовку
```

Корабль в строчке не назван ни разу — ни в перемене, ни во входе с уходом: она стоит в его же
цепочке, с его аватаркой и позывным над первой строкой, а полный титул в каждой сделал бы
из трёх перемен три почти одинаковых абзаца.
Номер — единственное, что показано парой: три цифры сами по себе ничего не значат, и «теперь 900»
осталось бы новостью без предмета; позывной и силуэт говорят за себя, а прежние стоят строчкой
выше в той же ленте.

Уход — единственная запись, где корабль добавляет свои слова: `course` приходит из шторки
прощания (`channel/LeaveRaid`) и хранится вместе с самой записью об уходе. Поле необязательное:
записи прежних уходов курса не знают, и им остаётся фраза с силуэтом — «Рейдовый тральщик
снялся с рейда». Длину курса бэкенд проверяет своим правилом: больше `MAX_COURSE_LENGTH` = 100
символов — отказ с кодом `course-too-long` и тем же текстом «Максимум 100 символов, у вас 101»
(`@/utils/limit`), и корабль остаётся на рейде.

Почему данными, а не готовой строкой: зашитая в хранилище фраза означала бы, что поправить
формулировку (или сказать её на другом языке) можно только правкой уже записанного. Бэкенд
отвечает за то, **что** случилось, интерфейс — за то, **как** об этом сказать; поэтому
`changed` приходит с бэкенда, а выделение изменившегося и порядок слов остаются в ленте.

Старший на рейде — `channel.owner`. Им становится тот, кто встал в канал первым, и остаётся,
пока не снимется с рейда; тогда старшинство переходит к тому, кто дольше всех стоит из оставшихся,
а вместе с ним приходит `channel-updated`. Ушли все — старшего снова нет. Высадить чужой корабль
может только он: `kick` адресуется его `memberId`, а высаживаемый идёт ссылкой в теле запроса.
Чужой вызов отклоняется с `not-senior`, и это не только про интерфейс — кнопку видно лишь
старшему, но правило живёт там, где данные. Со стороны канала высадка выглядит тем же
`member-left`, а в ленте отличается строчкой:

```
Пограничный сторожевой катер выдворен с рейда
```

— то есть тот же `ShipNotice`, только с `event: 'kicked'`. Снимок в `before` делает бэкенд:
он один знает, каким корабль был до правки, — и строчка остаётся про то, чем он был тогда,
даже если корабль потом переименуют ещё раз. Отдельного метода для системных записей нет:
их пишет сам канал.

### Отправить сообщение и ответить на него

```ts
const { message } = await backend.sendMessage({
    channelId,
    memberId: myId,
    message: { text: 'Швартовы отданы, выходим из бухты' },
});

// Ответ ссылается на сообщение, к которому привязан.
await backend.sendMessage({
    channelId,
    memberId: myId,
    message: { text: 'Идём следом, держу кильватер', thread: { messageId: message.messageId } },
});
```

Длину проверяет бэкенд, а не только форма: интерфейсов может стать больше одного, и правило
должно жить там, где данные. Больше `MAX_MESSAGE_LENGTH` = 500 символов — отказ с кодом
`message-too-long` и готовым текстом «Максимум 500 символов, у вас 505». Набранное при этом
не обрезается: обрезать чужой текст нельзя.

### Печать по проводу не идёт

Пока человек набирает, наружу не уходит ничего. Метода на это в контракте нет, события тоже:
по проводу идёт только то, что канал у себя оставляет.

Дело не в экономии. Событие на букву — это `query` + `onSnapshot`, то есть запись документа
на каждую букву: и дорого, и упирается в предел записей в один документ. Механика, которой
для работы нужен открытый сокет, на настоящем бэкенде просто не заводится, и лучше не иметь
её вовсе, чем иметь до первого переезда.

Видно при этом всё то же самое, потому что индикация не живая, а восстановленная. Сообщение
приходит целиком — и получатель печатает его у себя по буквам, быстро и чуть неровно, а корабль
отправителя всё это время мигает лампой и в шапке стоит «передаёт». Живёт это целиком
во фронтенде: `src/hooks/reception.ts` (арифметика) и `src/hooks/useReception.ts` (таймеры).

Мигание длиннее печати — знак Морзе идёт около секунды, а печатается за сотую её долю, —
поэтому лампа за буквами не гонится: текст режется на части не короче пяти знаков, и печать,
дойдя до границы части, переставляет передачу в то же место текста. Что мигание передало текст
целиком, никто не сверяет: это декорация. Честно уходят начало и конец — первую часть никто
не перебивает, а последнюю переставлять уже не с чего.

Свой набор — отдельный случай и совсем простой: лампа своего корабля мигает по набранному
без всякого деления. Передачи тут нет, всё происходит в одной вкладке, и вставленный разом
кусок текста лампа отыгрывает так же, как набранный по букве.

## События

У всех событий одинаковый конверт: `eventId`, `channelId`, `at`. Различает их только `type`.

```ts
type ChannelEvent = { eventId: string; channelId: string; at: number } & (
    | { type: 'channel-created'; channel: Channel }
    | { type: 'channel-updated'; channel: Channel }
    | { type: 'member-joined'; member: Member }
    | { type: 'member-updated'; member: Member }
    | { type: 'member-left'; member: MemberRef }
    | { type: 'message-added'; message: Message }
);
```

Формат расширяемый: чтобы добавить, например, системное уведомление о шторме, достаточно
дописать вариант в объединение. Транспорт и подписка про конкретные типы не знают,
а обработчик в UI разбирает знакомые и молча пропускает незнакомые:

```ts
switch (event.type) {
    case 'message-added':
        return { ...state, messages: [...state.messages, event.message] };
    // …
    default:
        return state; // незнакомое событие — не повод ломаться
}
```

## Ошибки

Отказ приходит отклонённым промисом с `ChannelError`. У него есть `code` для логики
и `message` — готовый текст для человека.

| `code`              | Когда                                          |
| ------------------- | ---------------------------------------------- |
| `channel-not-found` | Канала с таким id нет                          |
| `channel-full`      | На рейде не осталось свободного места          |
| `slug-invalid`      | В адресе есть что-то кроме букв, цифр и дефиса |
| `slug-taken`        | Адрес занят другим каналом                     |
| `name-taken`        | Позывной занят другим кораблём                 |
| `hull-taken`        | Бортовой номер занят                           |
| `member-not-found`  | Корабля с таким id в канале нет                |
| `not-senior`        | Высаживает не старший на рейде                 |
| `message-too-long`  | В сообщении больше 500 символов                |
| `course-too-long`   | В новом курсе больше 100 символов              |

## Что делает эмулятор

`LocalBackend` (`src/backend/localBackend.ts`) держит состояние «сервера» в `localStorage`
под ключом `kilvater.state`:

```json
{
    "version": 6,
    "channels": {
        "ch-demo": {
            "channel": { "channelId": "ch-demo", "slug": "demo", "title": "…", "createdAt": 0 },
            "members": [],
            "messages": []
        }
    }
}
```

Ключ в `channels` — это `channelId`. Поиск по адресу перебирает каналы и сравнивает `slug`;
у настоящего сервера тут был бы индекс.

- **Хранилище и провод разделены.** `localStorage` — память: пережил перезагрузку и отдал
  состояние тому, кто пришёл позже. `BroadcastChannel` — провод: доставил новость тем,
  кто уже здесь. Печать идёт только по проводу.
- **Задержка ответа 40 мс** стоит нарочно: у настоящего сервера мгновенных ответов не бывает,
  и интерфейс не должен рассчитывать, что состояние обновится к следующей строке кода.
- **Запись идёт по очереди, одна вкладка за раз.** Состояние лежит одним JSON-ом на весь
  браузер, и всякое изменение — это «прочитал целиком, поменял, записал целиком». В одной
  вкладке это неделимо: JS однопоточен. Вкладок две — и они читают одно состояние, а пишут
  каждая своё: записавшая второй стирает чужую правку, а место на рейде обе выбирают
  по своему снимку и обе видят его свободным. Поэтому каждая запись берёт общую блокировку
  (`navigator.locks`, `exclusive` в `localBackend.ts`), и внутрь неё уходит всё решение
  целиком — и проверки занятости, и расстановка, и сама запись. У настоящего сервера этой
  очередью занимается он сам; здесь она нужна ровно потому, что «сервер» размазан
  по вкладкам. Где блокировок нет (старый браузер, jsdom в юнит-тестах), код работает
  как раньше — без очереди, но и без второй вкладки рядом.
- **Демо-канал** (`src/backend/seed.ts`, id `ch-demo`, адрес `demo`) записывается при первом
  запуске, если хранилище пустое. Существующее состояние он не трогает.
- **Кто ты в канале — не дело бэкенда.** Память вкладки о себе лежит отдельно,
  в `sessionStorage` (`src/backend/identity.ts`), и в два уровня. Сверху — личность:
  `kilvater.identity`, один идентификатор на вкладку. Под ней связка каналов —
  `kilvater.crew.<identityId>`, объект `channelId → memberId`: чем эта личность стоит
  в каждом из каналов. Рядом `kilvater.look.<identityId>` — силуэт и цвет последнего
  корабля, ими открывается форма в канале, где эта личность ещё не стоит. В настоящей
  системе на месте личности был бы вход по токену, и вся связка досталась бы ему
  как есть — форма записи от этого не меняется. Записи прежней формы
  (`kilvater.member.<channelId>`, ключ на канал) подбираются при первом чтении канала
  и переезжают в связку.
- **Версия схемы** лежит в том же объекте, рядом с каналами. Несовпадение версии означает
  «привести к нынешней форме»: этим занят `src/backend/migrate.ts`, см. правило ниже.

## К чужим данным — бережно

Разговор в канале принадлежит не нам. Он не должен пропадать из-за того, что мы добавили
поле, переименовали ключ или выложили новую версию. Правило на будущее — из тех, что легко
нарушить один раз и потом объяснять людям, куда делась их переписка.

**Изменение контракта по умолчанию совместимое.** Новое поле — необязательное: либо
со значением по умолчанию, либо вычисляемое в момент чтения из того, что уже есть.
Несовместимым считается только то, чего действительно не восстановить: у поля поменялся
смысл, сущность разделилась надвое, идентификаторы перевыпущены. Всё остальное — совместимо.

Поле `tried` в `ShipPlacement` — пример именно совместимого изменения: у старого участника
его нет, и это ничему не мешает — на его месте читается `[place.corridor]`, то есть
«корабль стоял только там, где стоит». Ради такого выбрасывать переписку не за что.

**Версия — не разрешение стереть.** Она говорит «данные другой формы», и правильный ответ
на это — привести их к нынешней форме, а не начать с чистого листа. Приведение может быть
и ленивым, прямо при чтении: заполнить недостающее, досчитать выводимое, отбросить лишнее.

**Заход со старой версией ничего не ломает.** Что не разобрали — пропускаем молча, как
незнакомое событие в подписке; чего не хватает — достраиваем; что не сходится — оставляем
как есть, но не роняем экран и не трём соседнее.

**Как это устроено.** В `src/backend/migrate.ts` лежит таблица приведений: ключ — версия,
из которой приведение выводит, значение — функция в следующую форму. Состояние проходит
их по одной, ступенька за ступенькой, поэтому каждое приведение знает только свою пару форм
и пишется один раз — вместе с той правкой схемы, из-за которой версия и поднялась. Поднял
`STORAGE_VERSION` — положи туда функцию перехода; без неё разговор дальше этой выкладки
не проедет.

Разбор идёт всегда, даже когда версия совпала: битое состояние бывает и без смены схемы.
Канал, у которого не разобрались собственные поля, пропускается, соседние остаются; канал
без списков достраивается пустыми; участники и сообщения поштучно не проверяются вовсе —
незнакомое поле ничему не мешает, а недостающее читается запасным вариантом там, где
читается.

**Ничего не удаляется.** Даже то, что привести не удалось — форма старше всех приведений,
чужой JSON под нашим ключом, версия из будущей выкладки, — не переписывается поверх:
прежняя строка целиком уходит в `kilvater.state.was.<версия>` и дожидается там приведения,
которое сможет её забрать. По ключу на версию, так что копии не затирают друг друга.

## Почему данные в localStorage, а личность в sessionStorage

Разное время жизни у разного по смыслу. Канал — это «сервер»: он общий для всех вкладок
браузера и переживает перезагрузку, поэтому `localStorage`. Личность — это «кто сейчас
за пультом»: у каждой вкладки своя, поэтому `sessionStorage`.

Если бы личность тоже лежала в общем хранилище, вторая вкладка молча оказывалась бы
тем же кораблём — и поговорить было бы не с кем. С раздельным хранением новая вкладка
приходит в канал никем и встаёт в строй заново, как настоящий второй участник.

Плата за это — личность живёт до закрытия вкладки. Для эмулятора нормально: настоящий вход
появится вместе с настоящим бэкендом, и тогда `identity.ts` сменит хранилище на токен. Всё
своё сложено под личностью и адресуется ею, поэтому смена стоит одной строки: вход отдаёт
идентификатор личности вместо заведённого на месте, а связка каналов и внешность корабля
переезжают под него без переделки.

## Как проверить разговор двух кораблей

Открыть канал в новой вкладке и встать в строй ещё раз: данные канала общие, личность своя,
и на рейде окажутся два корабля.

Одна тонкость: вкладка, открытая **по ссылке** из уже открытой (Ctrl+клик, `target="_blank"`),
получает копию её `sessionStorage` и приходит тем же кораблём. Чтобы этого не было, откройте
пустую вкладку и вставьте адрес руками.

Если нужно войти именно за конкретный корабль, id можно передать в адресе:
`?channel=demo&memberId=m-albatros`. Параметр перебивает сохранённый id, но сам не
сохраняется, поэтому остальные вкладки остаются собой.
