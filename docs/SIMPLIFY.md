# Инструкция по упрощению «Кильватера»

Пошаговый план работ для агентов: как упростить машинерию манёвров, починить драг,
убрать «прижато скриптами вместо раскладки», ускорить проверки, дотюнить контракт
бэкенда. Дополняет [REVIEW.md](./REVIEW.md) (там — диагнозы, здесь — операции).
Номера строк — по коммиту `97664ea`; при расхождении ищи по именам функций и цитатам.

Коммит `97664ea` уже закрыл три пункта из REVIEW: TopFade удалён целиком (обход DOM
с `getComputedStyle` ушёл), шторки тянутся только за ручку с захватом указателя
(утечка window-слушателей и спор с нативной прокруткой ушли сами), рисочка ручки
сведена в один миксин (`src/grip.less`). Ниже — то, что осталось.

## Правила (читать перед любой правкой)

1. **Поведение — святое.** Тайминги, движения, метафора не меняются: корабль идёт свои
   26 секунд, кивает на остановке, качается в фазе своего места. Меняется только *способ*
   реализации. Если после правки что-то стало «быстрее и проще» на глаз — это регрессия.
   (Исключение одно и явное: в проверочном окружении время ускоряется множителем —
   см. этап 5, — но это настройка окружения, а не правка поведения.)
2. **Комментарии — часть кода.** Сокращаем логику, не прозу. Перенёс код — перенеси его
   комментарий; упростил логику — перепиши комментарий под новую, тем же тоном
   («почему», по-русски).
3. **Сетка безопасности** — `npm run check` и `npm run test:e2e`. Гонять e2e после
   каждого этапа, а не в конце. Упавшая проверка = регрессия поведения: чинить правку,
   а не проверку.
4. **По одному этапу за коммит.** Этапы независимы и упорядочены по выгоде/риску.
5. Оценка «сократить вдвое» честно выглядит так: минус 20–30% исполняемого кода
   (главные жертвы — ручное прижатие ленты, машинерия манёвров, дубли шторочных
   заголовков), плюс главный выигрыш не в строках, а в том, что `App.tsx` и
   `SeaScene.tsx` перестают быть местами, где всё связано со всем.

## Этап 1. Лента: прижатие раскладкой, а не скриптами

**Симптом (подтверждён, и это тот самый «трепыхающийся» чат):** при изменении размера
панели лента дёргается, пытаясь оторваться от низа. Причина: низ держат два скрипта,
бегущих вдогонку за раскладкой — `useLayoutEffect` без зависимостей ставит
`scrollTop = scrollHeight` после каждого рендера (`MessageList.tsx:115–132`), а
`ResizeObserver` повторяет то же на каждом кадре перехода высоты
(`MessageList.tsx:140–153`). Каждый кадр: браузер кладёт ленту по новой высоте (низ
уехал) → скрипт доматывает обратно. Между этими двумя моментами и живёт дрожь.

**Лечение: `flex-direction: column-reverse` на скроллере.** В обратной колонке
`scrollTop = 0` — это низ, и браузер держит его сам: ресайз панели, новое сообщение,
выросшая цитата — низ прижат раскладкой, скриптам делать нечего.

Порядок работ в `MessageList.tsx` / `MessageList.module.less`:

1. `.list` (module.less:4): `flex-direction: column` → `column-reverse`.
2. Сообщения рендерить в обратном порядке, чтобы визуальный порядок не изменился:
   `messages.toReversed().map(...)`. Группировку (`groupKeys`,
   `firstOfGroup`/`lastOfGroup`) считать ДО разворота, по исходному массиву, и сложить
   в `Map<messageId, {first, last}>` — при рендере в обратном порядке позиционные
   индексы врут, а Map читается от самого сообщения. Смысл «первый/последний в группе»
   хронологический и от порядка в разметке не зависит.
3. `dateChip` — сейчас первый ребёнок (`MessageList.tsx:287`); в обратной колонке
   первый в разметке = нижний, поэтому перенести его последним ребёнком (визуально
   останется сверху).
4. Удалить целиком: `stuckRef`, `topRef`, `handleScroll`, оба доводящих
   `useLayoutEffect` и `ResizeObserver` (MessageList.tsx:65–153, ~90 строк). Прицеп —
   больше не состояние, а положение прокрутки: `scrollTop === 0` значит «прицеплена».
5. Единственный оставшийся скрипт — «своя реплика прицепляет обратно»:

```tsx
// Своя реплика прицепляет ленту обратно: отправить сообщение и не увидеть его —
// единственный случай, когда «не мотать» читается поломкой. Всё остальное прижатие
// к низу делает сама раскладка: в обратной колонке низ — это scrollTop = 0,
// и браузер держит его через любой ресайз без нашей помощи.
const lastOwnRef = useRef(lastOwnId);
useLayoutEffect(() => {
    if (lastOwnId && lastOwnId !== lastOwnRef.current) {
        listRef.current?.scrollTo({ top: 0 });
    }
    lastOwnRef.current = lastOwnId;
}, [lastOwnId]);
```

6. `gap: 4px` и паддинги (`--feed-pad-*`) работают в column-reverse как есть; глазами
   проверить только полосу прокрутки (`scroll.less`) — маска считается от кромок блока
   и от направления не зависит.

Отмотавшему вверх читателю место держит сам браузер: CSS Scroll Anchoring
(`overflow-anchor: auto`, включён по умолчанию) компенсирует контент, вставленный
перед видимым, — новое сообщение в начале DOM читающего старое не сдвигает.

**Риски.** Скринридер читает DOM-порядок, после разворота — «новые сверху»; это
стандартная цена column-reverse (так живут чаты на нём), при желании потом смягчается
`role="log"` + `aria-live`. Колесо и PgUp/PgDn в column-reverse корректны во всех
современных браузерах; единственное, что стоит проверить глазами на живом iOS
Safari, — rubber-banding на границах контента (исторические баги column-reverse
в WebKit закрыты давно, но это дешёвая проверка). E2e «лента держится низа, пока её
не отмотали» и «не отцепляется, когда её окошко ужимает смена раскладки» обязаны
пройти без правок — они описывают поведение, а не способ.

**Сокращение:** ~90 строк → ~10.

## Этап 2. Драг мимо React

**Диагноз** (REVIEW §Фризы, после `97664ea` всё ещё в силе): каждый `pointermove`
проходит через `setState` и перерисовывает дерево. Свайп шторки — `setShift`
(`useSheetDrag.ts:151`) → поддерево шторки (или ВЕСЬ App, когда это приспуск `lower`,
App.tsx:657). Кромка разговора — `resize(from.open)` (`App.tsx:733`) → весь App через
состояние `useLayout`. Частота pointermove на тачах 60–120 Гц; сцена и лента рендерятся
с той же частотой. Правило починки: **во время жеста пишем стиль напрямую, React
узнаёт о жесте дважды — на захвате и на отпускании.**

После `97664ea` это стало проще: обработчики уже висят на ручке с захватом указателя,
window-слушателей нет, «спорщиков» за движение нет.

### 2.1 `useSheetDrag` (hooks/useSheetDrag.ts)

Хук перестаёт отдавать `shift` на каждый кадр и начинает двигать коробку сам. Ручка
лежит прямо в коробке (`box = grip.parentElement`, useSheetDrag.ts:112) — элемент уже
в руках, ref не нужен:

```ts
const onPointerMove = (event: ReactPointerEvent<HTMLElement>) => {
    const drag = runRef.current;
    if (drag?.pointerId !== event.pointerId) {
        return;
    }
    drag.moved = true;
    const way = event.clientY - drag.startAt;
    drag.fling.mark(drag.startOpen - way, event.timeStamp);
    const lowest = drag.points[0];
    const highest = drag.points[drag.points.length - 1];
    const opened = Math.min(Math.max(drag.startOpen - way, lowest), highest);
    drag.shift = drag.run - opened;
    // Мимо React: жест — это стиль, а не состояние. Дерево не перерисовывается
    // ни на один кадр движения пальца; чем нарисовать сдвиг, коробка сказала сама
    // (--drag-shift в её стилях).
    drag.box.style.setProperty('--drag-shift', `${drag.shift}px`);
};
```

- `drag.box` кладётся в `Run` на `onPointerDown` (там элемент уже есть).
- На `onPointerUp`: снять `--drag-shift` (`box.style.removeProperty`), и дальше как
  сейчас — `setDragging(false)` и `setShift(...)` одним заходом (один-два рендера на
  весь жест вместо сотни).
- В стилях коробок (`Shade.module.less` .shade, `App.module.less` .content/.form/.list)
  сдвиг читать из переменной: `translate: 0 calc(var(--drag-shift, 0px) + var(--lowered, 0px))`
  — у шторки сейчас inline-`transform` из `shift` (Shade.tsx:132), он заменяется
  на ту же переменную, которую после отпускания выставляет уже React из состояния
  `shift` (инлайном на коробке, как сейчас, — но только когда жест кончился).
- Затемнение шторки во время жеста (`opacity` от сдвига, Shade.tsx:121) — та же
  переменная: `opacity: clamp(0, 1 - var(--drag-shift, 0px) / 200px, 1)` не выразить
  в CSS без делений на px; проще писать и её из `onPointerMove` тем же
  `style.setProperty('opacity', ...)` по ref затемнения, который Shade передаёт хуку
  необязательным полем. Ничего страшного в двух строках прямой записи нет — важно, что
  React в жесте не участвует.

### 2.2 Приспуск коробки (`lower`, App.tsx:657) и кромка разговора (App.tsx:716–783)

- `--lowered` уже переменная на корне (App.tsx:829, `'--lowered': ${loweredNow}px`).
  Для приспуска достаточно, чтобы `useSheetDrag` во время жеста писал свою
  `--drag-shift` не в коробку, а в корневой элемент приложения (пробросить целевой
  элемент опцией хука), а рендерная `--lowered` осталась для положения «после
  отпускания». Формула в стилях: там, где сейчас `var(--lowered)`, станет
  `calc(var(--lowered) + var(--drag-shift, 0px))` (App.module.less .content/.form/.list
  и всё, что считает `--taken-to`).
- Внимание: от `lowered` зависят и `--taken-to`/`--chat-to` (App.tsx:680–691) — они
  тоже должны «ехать» во время жеста. Они уже выражения вида
  `max(X - lowered, 0)` — перевести их в CSS: `--taken-to:
  max(calc(Xpx - var(--lowered) - var(--drag-shift, 0px)), 0px)`, где X кладёт рендер
  (`layerBox`/`size` меняются только вне жеста). Тогда кадр поджимается за пальцем
  без единого рендера — тем же механизмом, каким сейчас едет по переходу.
- Кромка разговора (`handleGripMove`, App.tsx:726–734): то же самое — вместо
  `resize(from.open)` писать в корень `--chat-to`/`--taken-to`/`--box-to` прямыми
  значениями от `from.open` (формулы — те же, что в рендере: `chatBox`, `taken`;
  вынести их в маленькие чистые функции, чтобы рендер и жест не разъехались).
  На `handleGripUp` всё как сейчас: `resize(settled, true)` — один рендер.
- `setDragging(true/false)` — по разу на жест (классы `.appDragging`/`.appLowering`
  снимают переходы) — остаётся.

## Этап 4. Машинерия манёвров: из ref-ов в редьюсер

Самый дорогой и самый важный для будущего этап. Сейчас жизненный цикл манёвров размазан
по 15 ref-ам, мутируемым прямо в теле рендера (SeaScene.tsx:280–459), трём картам
таймеров и функции `finishMotion` (564–598), которая смешивает три разных перехода.
Фаза «пауза перезахода» вообще не имеет флага — она выводится «от противного» из трёх
множеств. Инварианты держатся на порядке операторов внутри рендера.

**Целевая форма:** новый модуль `src/components/SeaScene/fleetMotion.ts` — чистый
редьюсер машины состояний + тонкий хук. Геометрия (`shipMotion.ts`) не трогается
вовсе, только импортируется.

### 4.1 Типы

```ts
export type Phase = 'anchored' | 'entering' | 'leaving' | 'paused' | 'shifting';

export interface ShipMotion {
    phase: Phase;
    /** Что нарисовано в кадре. У уходящего — СТАРОЕ место и силуэт: с них он и уходит. */
    shown: { place: ShipPlacement; shipKind: ShipKind };
    /** Куда корабль встанет после паузы перезахода. Есть только у leaving/paused с course. */
    target?: { place: ShipPlacement; shipKind: ShipKind };
    /** Обе стороны манёвра перезахода, посчитанные один раз. */
    course?: RelocateCourse;
    /** Есть только у phase === 'shifting'. */
    shift?: Shift;
    /** Кивок — независимый бит поверх фазы, а не фаза: он накладывается и на ход, и на стоянку. */
    nodding: boolean;
    /** Настоящее время начала текущего хода — для подводки анимаций после фоновой вкладки. */
    motionStartedAt?: number;
}

export type FleetEvent =
    | { type: 'members'; members: Member[]; ready: boolean; now: number }
    | { type: 'motion-end'; id: string }   // transitionend ИЛИ страховочный таймер — одинаково
    | { type: 'pause-end'; id: string }
    | { type: 'nod-start'; id: string }
    | { type: 'nod-end'; id: string };

export interface TimerRequest {
    id: string;
    kind: 'pause' | 'nod-lead' | 'nod-end' | 'motion-grace';
    ms: number;
}

export const reduce = (
    state: Map<string, ShipMotion>,
    event: FleetEvent
): { state: Map<string, ShipMotion>; effects: TimerRequest[] } => { ... };
```

### 4.2 Переходы (переносится один в один из нынешнего кода)

- `members`, новый id → `entering` (сейчас SeaScene.tsx:389–393).
- `members`, id пропал → `leaving` без `course` (сейчас 397–403).
- `members`, id вернулся, пока `leaving` без course → сразу `anchored`, ход обрывается
  (сейчас 453–459 — этот путь минует finishMotion, в редьюсере он становится обычной
  веткой, и таймеры этого id гасятся штатно).
- `members`, сменилось место/силуэт/курс → `shiftAcross` даёт `shift` → `shifting`
  (shown обновляется сразу — идёт по воде); иначе `leaving` с `course` и `target`,
  а **`shown` остаётся старым** (сейчас 416–449; уходящий обязан уходить со старого
  места — это ловушка №1, см. 4.4).
- `motion-end` при `leaving` с course → `paused` + эффект `{kind:'pause',
  ms: RELOCATE_PAUSE_MS}`; при `leaving` без course → удалить из карты; при
  `entering`/`shifting` → `anchored` (сейчас всё это — ветвление finishMotion 564–598).
- `pause-end` → `entering`, `shown = target` (сейчас таймер 588–596).
- `nod-start`/`nod-end` → бит `nodding` (сейчас startNod/scheduleNod 533–553 +
  noddingIds/nodTimers).

**Кивок можно снять с таймеров ещё до редьюсера** (совместимо с ним и с ним же
упрощается): момент старта `nod-down` — это `calc()` от уже существующих переменных,
а не подгаданный setTimeout. Кивок на трогании (`nod-up`) уже так и живёт — висит
на классах движения в чистом CSS (SeaScene.module.less:1140). Для остановки:

```less
// NOD_SECONDS * NOD_LEAD = 2.8s — перенести из JS именованной константой, не на глаз.
@nod-lead-offset: 2.8s;

.shipEntering .shipNod {
    animation: nod-down @nod-seconds @wave-ease calc(var(--enter-seconds) - @nod-lead-offset) both;
}
```

Конец кивка ловить `onAnimationEnd` (проверив `animationName`) вместо второго
таймера. Тонкость: класс движения снимается по transitionend раньше, чем кивок
доиграет (~0.7 с хвоста), поэтому кивковую анимацию держит отдельный класс-состояние
(«оседает»), который ставится вместе с движением и снимается по animationend, а не
таймером. Проверить глазами короткие переходы по воде, где `nod-up` и `nod-down`
перекрываются: кто «сверху» при наложении двух анимаций одного свойства — самая
браузерозависимая часть, сейчас её разруливает порядок классов в каскаде
(комментарий у SeaScene.module.less:1147 «побеждать должна остановка»).

### 4.3 Подключение в компоненте

```tsx
const [fleet, dispatchFleet] = useFleetMotion(); // useReducer + таймеры внутри хука
useLayoutEffect(() => {
    dispatchFleet({ type: 'members', members, ready, now: Date.now() });
}, [members, ready]);
```

Хук `useFleetMotion` держит `useReducer(reduce, new Map())` и одну карту живых
таймеров: после каждого dispatch заводит `window.setTimeout` по списку `effects`
(время — от `Date.now()` на момент dispatch, чистый setTimeout, НЕ завязанный на
рендер: страховка обязана тикать и в фоновой вкладке — сейчас это свойство
`motionTimers`, его нельзя потерять) и диспатчит `motion-end`/`pause-end`/`nod-*`
обратно. `redraw`-счётчик (SeaScene.tsx:313) умирает: dispatch сам вызывает рендер.

В JSX вместо жонглирования пятью множествами (SeaScene.tsx:959–967):

```tsx
const motion = fleet.get(member.memberId);
const leaving = motion?.phase === 'leaving';
const entering = motion?.phase === 'entering';
// paused вообще не рисуется — раньше это выводилось «от противного» из трёх Set-ов.
```

`placed` = участники с фазой не `paused`/не отсутствующей + синтетические «двойники»
из записей `leaving` (данные — из `motion.shown`).

### 4.4 Ловушки (инварианты, которые нельзя потерять)

1. **Уходящий рисуется со старым местом.** Сейчас: `leavingById.set(id,
   {...member, ...shown})` (SeaScene.tsx:437). В новой форме `shown` при входе в
   `leaving` НЕ обновляется (новое — в `target`); `shown` меняется только на
   `pause-end`. Перепутаешь — уходящий телепортируется на новое место.
2. **Перезаходящий не рисуется вовсе между уходом и заходом** — это фаза `paused`,
   у неё теперь есть имя; фильтр `placed` обязан её исключать.
3. **Фаза качки — от места, не от корабля** (`wavePhase(place)`, SeaScene.tsx:84–86).
   В редьюсер её не переносить: она остаётся в компоненте и для leaving-двойника
   считается от `motion.shown.place`.
4. **Подводка анимаций после фоновой вкладки** (SeaScene.tsx:607–644):
   `motionStartedAt` пишется только при СМЕНЕ вида движения — в редьюсере это «только
   при смене phase», не на каждый dispatch. Resync по `visibilitychange` трогает
   только DOM-анимации и в машину не диспатчит ничего — так и оставить.
5. **`motion-end` идемпотентен и един для двух источников** (transitionend и
   страховка MOTION_GRACE_MS): второй вызов по тому же id должен быть no-op — в
   редьюсере это естественно (фаза уже не движение), но покрыть тестом.

### 4.5 Юнит-тесты нового модуля (`fleetMotion.test.ts`, стиль — как shipMotion.test.ts)

- перезаход = leaving → paused → entering, `course` не пересчитывается по дороге,
  `shown` меняется только на pause-end;
- возврат того же id во время ухода → anchored сразу, без entering;
- страховочный `motion-end` без transitionend завершает ход так же, как настоящий,
  а повторный `motion-end` — no-op;
- переход по воде (shifting) не проходит через leaving/paused;
- уход насовсем удаляет запись, и повторный вход того же id — снова entering.

**Сокращение:** из SeaScene.tsx уходит ~200 строк самого хрупкого кода (280–330,
383–459, 516–598), в `fleetMotion.ts` появляется ~250 строк, из которых половина —
типы и комментарии, и ВСЁ это покрыто юнитами. SeaScene.tsx остаётся про рисование.

## Этап 5. Медленные проверки: событийные ожидания и ускоренное время

Полный прогон — 6+ минут на ~125 проверок (см. docs/TODO.md, там верный диагноз).
Две причины, чинятся независимо; вместе дают минус ~4 минуты из шести.

### 5.1 Фиксированные sleep-ы в каждом тесте (дёшево, без риска)

`tests/helpers.ts`: `openChannel`/`openNewChannel` ждут `SCENE_READY_MS = 1500` мс
**фиксированно** (helpers.ts:17–33, 45). 125 проверок × 1.5 c ≈ **3 минуты чистого
сна** — больше, чем четыре «длинных» теста вместе. Сцена сообщает о готовности классом
(`scenePainted`, SeaScene.tsx:919) — ждать её, а не таймер:

```ts
// Сцена проявляется, когда догрузились задники (см. scenePainted в SeaScene) —
// ждём её, а не таймер: на быстрой машине это сотни миллисекунд, а не полторы секунды.
await expect(page.locator('[class*="scenePainted"]')).toBeVisible();
```

(Надёжнее — повесить в сцене `data-scene-ready` и ждать его: класс хеширован CSS
Modules, `class*=` держится на подстроке имени. Одна строка в SeaScene.)
То же с `WRITE_MS = 300` (helpers.ts:57): вместо сна опрашивать хранилище
`expect.poll(() => page.evaluate(...))` — там, где он реально нужен.

### 5.2 Ускоренное время (их же TODO, вот конкретная механика)

Все длительности приложения уже собраны в двух местах: `src/motion.less`
(@expand/@slide/@berth-fade) + переменные `--enter-seconds`/`--leave-seconds`/…,
которые компонент считает из `sailSeconds` (`shipMotion.ts:192–195`). Это делает
множитель дешёвым:

1. Завести `src/config/time.ts`:

```ts
/**
 * Во сколько раз ускорено время. В жизни — единица; проверочный прогон ставит десятку
 * через query (?fast=10): ход остаётся ходом и проходит те же кадры, просто быстрее.
 * Обнулять длительности нельзя — часть проверок смотрит на промежуточные кадры
 * (см. TODO «не путать ускорение с отключением»).
 */
export const timeScale = (): number => {
    const fast = new URLSearchParams(window.location.search).get('fast');
    const scale = fast ? Number(fast) : 1;
    return Number.isFinite(scale) && scale >= 1 ? scale : 1;
};
```

2. В `index.tsx` при старте: `document.documentElement.style.setProperty('--time-scale',
   String(timeScale()))`.
3. В `motion.less` длительности обернуть: `@expand-seconds: ~'calc(0.42s /
   var(--time-scale, 1))'` (и так же @slide, @berth-fade; @wave-duration НЕ трогать —
   качка не «движение к цели», её ускорение только собьёт фазу с реальным временем
   ожиданий, а проверки её не ждут).
4. В `shipMotion.ts` `sailSeconds(...)` делить результат на `timeScale()` (одно место,
   shipMotion.ts:192–195). JS-таймеры сцены (`RELOCATE_PAUSE_MS`, NOD_*, GRACE) читают
   длительности с элементов и констант — паузу и кивок тоже поделить на `timeScale()`
   в местах употребления (SeaScene.tsx:121, 126, 552, 616).
5. В `tests/helpers.ts` `openChannel` добавляет `&fast=10` по умолчанию, с опцией
   `{ realTime: true }` для покадровых проверок (те, что «смотрят на промежуточные
   кадры»: разворот сцены, вода без скачка — им нужен просто короткий, не нулевой ход,
   `fast=10` им тоже подходит; `realTime` — страховка на случай, если какая-то
   проверка завязана на абсолютные миллисекунды).

Итог по TODO-таблице: «55.2s + 42.6s + 36.4s + 20.0s» превращаются в ~15 секунд
суммарно. Заодно `timeout: 120_000` в `playwright.config.ts:28` можно опустить до
30–40 с — упавшие проверки перестанут висеть по две минуты.

## Этап 6. Контракт бэкенда: дотюнить до Firebase

Диагнозы — REVIEW §Контракты. Операции, в порядке ценности:

### 6.1 Самолечение хранилища — только под замком

`readState` (localBackend.ts:86–107) при несовпадении версии/битом JSON пишет свежее
состояние прямо из чтения, а зовётся и без очереди — из `getChannel` (:268),
`getChannelBySlug` (:271), старта (:178). Правка:

- `readState` при несовпадении возвращает `{ version: STORAGE_VERSION, channels: {} }`
  **без записи**;
- сброс с демо-каналом — отдельная `ensureState()`, вызываемая один раз из
  `createLocalBackend` **внутри `exclusive()`**: прочитала, увидела пустоту — положила
  демо-канал и записала. Читающие пути больше не пишут никогда.

### 6.2 Отказ записи — не молчание

`utils/storage.ts:36–42`: `write` возвращает `boolean`; `writeState`
(localBackend.ts:109–111) кидает `ChannelError('storage-full', 'Не удалось сохранить:
хранилище переполнено или недоступно')` (новый код в `ChannelErrorCode`). UI уже умеет
показывать `ChannelError` снекбаром (App.tsx: handleSend/handleLeaveConfirm) — дойдёт
само. Прочие вызовы `write` (identity, layout) осознанно молчат — им и надо.

### 6.3 Членство в sendMessage

localBackend.ts:478–482: перед публикацией — `if (!snapshot.members.some(m =>
m.memberId === memberId)) throw new ChannelError('member-not-found', 'Отправитель не
в составе канала')` (код уже существует в types.ts). Ветка `author ? ... : {memberId}`
остаётся — она для старых записей в ленте, не для живой отправки.

### 6.4 Пагинация сообщений — в контракт, до Firebase

В `ChannelBackend` (types.ts, рядом с getChannelBySlug):

```ts
export interface MessagesPage {
    items: Message[];
    /** Курсор старшей страницы: передать в before, чтобы листать глубже. Нет — история кончилась. */
    nextCursor?: string;
}
// В ChannelBackend:
/** Страница истории до курсора. Снапшот канала несёт только последнюю страницу. */
getMessages(request: { channelId: string; before?: string; limit?: number }): Promise<MessagesPage>;
```

Реализация в эмуляторе — срез массива (десяток строк). `ChannelSnapshot.messages`
документируется как «последняя страница» (docs/BACKEND-API.md). Потребители, которые
сейчас полагаются на «messages — вся история»: поиск цитируемого
(MessageList.tsx:363–365 — после правки честно показывает цитату «недогруженного»
по снимку из `thread`, если добавить в `MessageRef` снимок текста — решить при
реализации) и дедуп в useChannel.ts:123. UI-подгрузку при прокрутке можно не делать
сейчас — важно, чтобы контракт и вызывающие перестали обещать «всю историю».

### 6.5 Монотонный порядок

В `Message` (types/channel.ts) — необязательное `seq?: number`; в снапшоте канала —
счётчик `nextSeq`, проставляемый в `sendMessage` и `postNotice` под тем же замком.
Комментарий: «порядок ленты; sentAt — часы клиента и годится только для показа

### 6.6 Код `unavailable` + заготовка миграций

- В `ChannelErrorCode` добавить `'unavailable'` с комментарием «сеть/бэкенд недоступны;

  catch-ом (сейчас его нет — useChannel.ts:61–83): показать состояние «нет связи»

- Рядом со `STORAGE_VERSION` — пустая карта миграций как закреплённая граница
