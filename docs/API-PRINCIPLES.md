# Принципы разработки API

Контракт живёт дольше кода, который его читает. Почти всё, что в нём больно менять,
больно потому, что однажды поле сделали на один размер меньше, чем нужно: строкой вместо
объекта, списком идентификаторов вместо списка объектов, флагом вместо перечисления.
Правила ниже — про то, как оставить место для завтрашнего поля, не платя за это сегодня.

Проверка простая: **что придётся сломать, если сюда понадобится добавить ещё одно поле?**
Если ответ «ничего, допишу рядом» — контракт в порядке.

## Форма данных

**Всё, что может стать объектом, кладём объектом.** Даже когда прямо сейчас нужно
одно поле. Понадобилось имя участника — в контракт идёт не `memberName`, а `member`
с полем имени. Когда завтра понадобится ещё и цвет позывного, он допишется внутрь `member`,
а не встанет вторым плоским полем `memberColor` рядом с первым.

```ts
// Плохо: расширяется только новыми полями по соседству, и связь между ними видна лишь по имени.
const bad = { memberName: 'Гроза', memberColor: '#8ecae6' };

// Хорошо: место для любых полей участника уже есть.
const good = { member: { memberId: 'm-1', name: 'Гроза', color: '#8ecae6' } };
```

**Списки — списки объектов, а не идентификаторов.** Это тот же принцип, но ошибка здесь
дороже: массив строк расширить нечем, и переход к объектам ломает всех читателей разом.

```ts
// Плохо: понадобились имена — контракт менять целиком.
const bad = { members: ['m-1', 'm-2'] };

// Хорошо: имена, цвета и что угодно ещё дописываются внутрь элемента.
const good = { members: [{ memberId: 'm-1' }, { memberId: 'm-2' }] };
```

**Поле-ссылка называется по сущности и внутри несёт её канонический идентификатор.**
У сущности ровно одно имя идентификатора — `<сущность>Id`, — и оно одинаково везде:
и в самой сущности, и в ссылке на неё. Тогда ссылку не нужно переводить в сущность
по памяти: `message.author.memberId` и `member.memberId` — одно и то же поле.

**В одном объекте — поля одной сущности.** Если ответу нужны часть канала и часть
участника, это два ключа, а не общая куча:

```ts
// Плохо: чьё поле title, а чьё name — понятно только из головы.
const bad = { channelId: 'ch-1', title: 'Полночь', memberId: 'm-1', name: 'Гроза' };

// Хорошо.
const good = {
    channel: { channelId: 'ch-1', title: 'Полночь' },
    member: { memberId: 'm-1', name: 'Гроза' },
};
```

**Ответ — всегда объект.** Никогда голый массив и никогда голый скаляр: и то и другое
некуда расширять. Список отдаём как `{ items: [...] }` — рядом однажды встанут `nextCursor`
или `total`, и это не будет ломающим изменением. То же и в запросах: тело — объект,
организованный по тем же правилам.

**Не кодируем несколько значений в одну строку.** Никаких `"3:left"` и `"m-1|Гроза"`.
Составное значение — объект с полями; разбирать строку получателю не полагается.

## Типы значений

**Идентификаторы — строки.** Всегда, даже когда сегодня это счётчик. Число в идентификаторе
однажды перестанет помещаться, станет составным или уедет в другую систему нумерации,
и все, кто складывал его в `number`, окажутся неправы.

**Вариативные значения — перечисления.** Не свободная строка и не число: `corridor: 'left'`,
а не `corridor: 0`; `shipKind: 'patrol'`, а не `shipKind: 3`. Число экономит буквы и стоит
читателю знания таблицы, которой у него нет.

**Перечисление расширяемо, и получатель это переживает.** Незнакомое значение — не повод
падать: разбираем знакомые, остальные пропускаем молча, как незнакомый тип события в подписке.
Поэтому же перечисление никогда не заменяет `boolean` задним числом — если состояний может
стать больше двух, перечисление ставим сразу.

**Время — число, миллисекунды эпохи.** Как показать — дело интерфейса, а не контракта.

**Необязательное поле означает «может не быть».** Не «бывает `null`», не «бывает пустой
строкой» — одно из двух, последовательно по всему контракту.

## Функции и хуки

**Принимаем объект с именованными полями.** Позиционные аргументы читаются на месте вызова
как загадка, особенно когда подряд идут два одинаковых типа: `move(a, b)` — кто из них куда?
Объект называет поля, разрешает пропускать необязательное и добавлять новое, не трогая
существующие вызовы.

```ts
// Плохо: два string подряд, порядок помнить наизусть.
setTyping(channelId, memberId, chars);

// Хорошо.
setTyping({ channelId, memberId, typing: { chars } });
```

**Ключевые адресные параметры остаются скалярами.** То, что в настоящем API стояло бы
в пути или в query — `channelId`, `memberId`, — приходит отдельными полями, а не завёрнутым
в объект: это адрес запроса, а не его содержимое. Содержимое — рядом, своим ключом.

## Эволюция

**Добавление поля — совместимое изменение.** Удаление, переименование и смена смысла — нет.
Необязательные поля не переиспользуем под другой смысл: проще завести новое, чем искать всех,
кто понял старое по-своему.

**Получатель игнорирует незнакомое.** Лишние поля в ответе, незнакомый тип события, новое
значение перечисления — всё это не ошибка. Строгая проверка «ровно эти поля» превращает любое
расширение в ломающее.

**Ошибка — объект с машинным кодом и человеческим текстом.** Код из перечисления, для логики;
текст для показа. Коды добавляются, но не переименовываются: по ним написаны ветки у читателей.

**К данным относимся бережно.** Отдельное правило про хранимое состояние и версии схемы —
в [BACKEND-API.md](./BACKEND-API.md#к-чужим-данным--бережно).

## Что у нас уже так

Контракт (`src/backend/types.ts`, `src/types/channel.ts`) приведён к этим правилам целиком:

- сущность отделена от коллекций: `ChannelSnapshot` — это `{ channel, members, messages }`;
- у сущности один идентификатор, и в ссылке он называется так же: `member.memberId`
  и `message.author.memberId` — одно и то же поле;
- ссылки — объекты: `author: { memberId }`, `thread: { messageId }`,
  `member-left { member: { memberId } }`, `typing { member, typing: { chars } }`;
- методы принимают один именованный объект, адресные поля лежат в нём скалярами;
- ответы завёрнуты: `join` → `{ member }`, `sendMessage` → `{ message }`,
  `createChannel` → `{ channel }`;
- `channel-updated` несёт канал целиком, а не плоские `slug` и `title`;
- вариативные значения — перечисления: `Corridor` = `'left' | 'center' | 'right'`,
  `ShipKind`, `ChannelErrorCode`;
- повторяющееся `'left' | 'right'` названо `Side`;
- все идентификаторы — строки, время — миллисекундами эпохи;
- ошибка — объект с машинным `code` и человеческим `message`;
- события — общий конверт плюс `type`, незнакомые типы UI пропускает молча.
