# Клавиатура на мобиле: что она делает с окном и как это дебажить

Ответ на «она сжимает окно или как-то особым образом сдвигает блоки?» — и то,
и другое, но по-разному на разных платформах, и сейчас код смотрит не туда.
По состоянию `97664ea`.

## Механика: два вьюпорта

У страницы два вьюпорта:

- **layout viewport** — от него считаются `100dvh/vh`, `position: fixed`,
  медиазапросы. Клавиатура его **по умолчанию не меняет нигде**: ни на iOS,
  ни на Android Chrome (с 108-й версии, режим `resizes-visual`).
- **visual viewport** — то, что реально видно. Клавиатура жмёт его всегда.
  Доступен из JS: `window.visualViewport` (`height`, `offsetTop`, события
  `resize`/`scroll`).

Когда фокус уходит в поле, браузер не «сдвигает блоки» — он **панорамирует
visual viewport внутри layout viewport**, чтобы поле было видно. Страница при
этом не прокручивается (наш `overflow: clip` тут ни при чём и правильно стоит),
просто «камера» съезжает. Отсюда и ощущение поломанного флоу: раскладка думает,
что окно прежнее, а видно другое.

Платформенные отличия:

| | layout viewport (dvh, fixed) | window.innerHeight | visualViewport.height |
| --- | --- | --- | --- |
| iOS Safari | не меняется | **уменьшается** | уменьшается |
| Android Chrome (по умолч.) | не меняется | не меняется | уменьшается |
| Android + `interactive-widget=resizes-content` | **уменьшается** | уменьшается | уменьшается |

## Почему у нас ломается

Код держит **два источника правды, и оба неверные при клавиатуре**:

- CSS меряет от `100dvh` (`.app`, `--scene-min` — App.module.less:24, 65)
  с комментарием «dvh, чтобы выехавшая клавиатура уменьшала именно доступную
  высоту» — **это не выполняется ни на одной платформе**: dvh реагирует на
  сворачивание браузерного хрома, но не на клавиатуру.
- JS меряет от `window.innerHeight` (`useWindowShape`, hooks/useLayout.ts).

На iOS клавиатура уменьшает `innerHeight`, но не dvh → JS пересчитывает раскладку
под новое число, CSS остаётся в старом → сцена и коробка разъезжаются, и всё это
ещё и едет переходами (resize-событие ставит `window-resizing` и переходы гасит,
но только на время самого события — а расхождение остаётся). На Android по
умолчанию не меняется ничего → браузер просто панорамирует, композер оказывается
под клавиатурой, и куда уехал кадр — решает браузер, а не раскладка.

## Как чинить: один источник — visualViewport

Правило то же, что во всей раскладке: **одно число, все от него считаются.**

1. В `useWindowShape` подписаться на `visualViewport` и мерить его:

```ts
const viewportHeight = () => Math.round(window.visualViewport?.height ?? window.innerHeight);
// подписки: visualViewport.addEventListener('resize', onResize) + существующий window resize.
// Синхронно, как сейчас: RESIZING_MARK ставится до пересчёта стилей — механизм уже есть
// и переиспользуется как есть (клавиатура — тот же «окно меняет размер»).
```

2. Число публиковать переменной на `<html>` — синхронно, там же, где ставится
   `RESIZING_MARK`:

```ts
document.documentElement.style.setProperty('--viewport-height', `${viewportHeight()}px`);
```

3. В стилях всё, что меряется `100dvh`, перевести на
   `var(--viewport-height, 100dvh)` (`.app` height, `--scene-height-to`,
   `--scene-min` — три места в App.module.less). Фолбэк оставляет прежнее
   поведение до первого замера и в старых браузерах.

4. **Политика сцены под клавиатурой:** с клавиатурой высоты на «сцену не ниже
   минимума» может не хватить (scene-min 300px + разговор + клавиатура > экран).
   Разрешить сцене уходить ниже `--scene-min`, пока открыта клавиатура: кадр
   в этот момент не главное — человек пишет. Признак «клавиатура открыта» не
   нужен отдельно: просто считать `--scene-min` тоже от `--viewport-height`
   долей, а не от dvh, — минимум сожмётся вместе с окном.

5. `interactive-widget=resizes-content` в meta **не добавлять**: он чинит только
   Android, дублирует var-путь вторым пересчётом и ничего не даёт iOS. Один
   var-путь работает везде одинаково. (Chromium-only `navigator.virtualKeyboard`
   / `env(keyboard-inset-height)` — по той же причине не основа.)

6. `visualViewport.offsetTop` (панорамирование) при таком устройстве остаётся
   нулевым или почти нулевым: раскладка сама ужимается под видимое, браузеру
   нечего панорамировать. Если на iOS фокус всё же дёргает панораму — это
   признак, что что-то ещё меряется от layout viewport; лечится тем же числом,
   не борьбой с браузером.

## Как это воспроизводить и дебажить

**В панели разработчика клавиатура не эмулируется** — ни device mode, ни CDP
настоящую IME не поднимают. Поэтому:

- **Главный выигрыш var-архитектуры — клавиатура становится числом.** После
  правки выше «открылась клавиатура» = «--viewport-height стал меньше на 300».
  Это воспроизводится прямо в DevTools: Elements → `<html>` → поменять
  `--viewport-height` руками (или в консоли
  `document.documentElement.style.setProperty('--viewport-height','420px')`)
  — и весь сценарий «клавиатура выехала/уехала» отлаживается на десктопе,
  покадрово, без телефона. Это же — готовый рычаг для будущих e2e-проверок.
- **Настоящее устройство, полноценный DevTools:**
  - Android: `chrome://inspect` на десктопе + USB-отладка — консоль, элементы
    и перформанс живого телефона.
  - iPhone: Safari на маке → меню Develop → телефон. (iOS без мака —
    только оверлей-консоль, см. ниже.)
  - В консоли смотреть соотношение трёх высот и событий:

```js
const log = (t) => console.log(t,
    'vv', Math.round(visualViewport.height), '+' + Math.round(visualViewport.offsetTop),
    'inner', innerHeight, 'dvh-root', document.documentElement.clientHeight);
['resize', 'scroll'].forEach((t) => visualViewport.addEventListener(t, () => log('vv:' + t)));
window.addEventListener('resize', () => log('win:resize'));
```

  Именно эта тройка отвечает на «сжимает или сдвигает»: если `vv` уменьшился,
  а `inner` нет — Android панорамирует; уменьшились оба, а `dvh-root` нет — iOS;
  все три — resizes-content.
- **Без компьютера:** оверлей-консоль eruda за query-флагом — дёшево и хватает
  для чисел выше:

```html
<!-- index.html, только под ?debug -->
<script>
    if (new URLSearchParams(location.search).has('debug')) {
        const s = document.createElement('script');
        s.src = 'https://cdn.jsdelivr.net/npm/eruda';
        s.onload = () => eruda.init();
        document.body.append(s);
    }
</script>
```

- Playwright клавиатуру тоже не поднимает — сценарии с ней проверяются либо
  подменой `--viewport-height` (после правки — честная проверка почти всего),
  либо руками на устройстве.

## Что проверить после починки (руками, на обеих платформах)

- фокус в композер: коробка разговора и сцена ужались одним движением, композер
  над клавиатурой, шапка на месте, ничего не «уехало камерой»;
- закрытие клавиатуры возвращает всё в прежний размер без прыжка (переходы
  на время смены сняты `window-resizing` — уже работает);
- фокус в поле формы корабля (слой) и в поле прощания (модальная шторка) — то же;
- поворот с открытой клавиатурой; появление плашки ответа при открытой клавиатуре;
- iOS: двойное нажатие в поле, свайп клавиатуры вниз, автоподстановка — панорама
  (`visualViewport.offsetTop`) остаётся у нуля.
